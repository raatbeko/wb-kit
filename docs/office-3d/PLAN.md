# WB Office 3D — план (локальная версия)

Ветка `office-3d`. Ветка `main` остаётся как есть: zip с кодом + один чат Claude Code у клиента.
Здесь мы поверх того же набора добавляем **3D-офис на ноутбуке клиента**: локальный сайт `localhost`, на котором видно, как сотрудники-агенты работают с магазином на Wildberries.

---

## 1. Главная идея: «Claude Code — мозг, 3D-офис — окно»

```
 Ноутбук клиента
 ├─ Claude Code (подписка клиента)
 │    клиент пишет /office или «что с остатками?», одобряет изменения в кабинете
 │    └─ хуки Claude Code: агент начал / закончил / ждёт «да»  ──┐
 ├─ wb-kit (как сейчас): MCP WB, роли .claude/agents, аудит,   │
 │    конкуренты, карточка, reports/                            │
 │                                                              ▼
 ├─ data/office.db  (SQLite)  ◄── события агентов, данные WB, отчёты, задачи
 │                                                              │
 └─ npm run office:web  →  http://localhost:3000                │
      локальный сервер читает SQLite и отдаёт события вживую (SSE)
      3D-сцена: персонажи печатают, «!» над тем, кто ждёт решения,
      KPI на экранах, отчёты и графики по клику
```

### Почему так, а не облако
- **Правила Anthropic.** Клиент сам работает в своём Claude Code на своей подписке, а наше приложение только показывает результат. Это обычное использование Claude Code. Гонять подписку клиента «под капотом» как движок нашего продукта нельзя.
- **Ключи** WB и MPSTATS лежат в `.env` на ноутбуке, как сейчас. Сервера, с которого они могут утечь, нет.
- **Ноль расходов на хостинг.** Токены Claude оплачивает подписка клиента.
- **80% кода уже есть.**

### Режим «Одобрить прямо в офисе» (по желанию)
Если клиент хочет нажимать «Одобрить» в 3D-офисе без чата, он вписывает **свой** `ANTHROPIC_API_KEY` в `.env`. Тогда локальный сервер сам запускает роли через Agent SDK (это разрешено: ключ API, оплата по токенам клиента). Без ключа офис работает в режиме «окна».

## 2. База данных — SQLite

Один файл: `data/office.db` (в `.gitignore`). Без установки и сервера, копируется вместе с папкой.

- **Драйвер:** `better-sqlite3` 12.x: готовые сборки для Windows и Mac, работает с Node 20–26. Встроенный `node:sqlite` не подошёл, ему нужен Node ≥ 22.13, а у клиентов бывает старее. Версия 13.x падала на Node 22.10.
- **Режим WAL:** хуки Claude Code пишут, а веб-сервер одновременно читает.
- **Миграции:** папка `office/db/migrations/*.sql` с номером версии в `PRAGMA user_version`, применяются при запуске.

### Таблицы (первая версия)

| Таблица | Что хранит | Кто пишет |
|---|---|---|
| `agents` | Сотрудники: id роли, имя, должность, место в офисе, текущий статус | Сервер при старте, хуки |
| `events` | Лента событий: агент начал, шаг, закончил, ошибка, ждёт решения | Хуки Claude Code, сервер |
| `tasks` | Задачи: вопрос, кто делает, статус, ссылка на результат | Хуки, сервер (режим API) |
| `approvals` | Предложенные изменения «было → станет», статус (ждёт / одобрено / отклонено / выполнено) | Роли через сервер, хуки |
| `reports` | Отчёты: тип (аудит, офис, конкуренты, карточка, свой), дата, путь в `reports/`, краткая сводка JSON | Скрипты аудита и офиса |
| `report_templates` | Шаблоны отчётника: запрос словами, SQL/описание, расписание | Отчётник |
| `wb_snapshot_*` | Кэш данных WB: продажи по дням, остатки, отзывы, финансы, реклама + время обновления | Синхронизация |
| `kpi_daily` | Готовые цифры для экранов в офисе: заказы, выручка, ДРР, остатки в днях | Синхронизация |
| `settings` | Настройки офиса: имя магазина, расписания, себестоимость товаров | Интерфейс |

Кэш WB в SQLite решает проблему лимитов: роли и экраны офиса читают базу, а в WB ходим только по расписанию, по одному отчёту в минуту.

## 3. Как Claude Code сообщает офису, что происходит

Хуки в `.claude/settings.json` вызывают `node office/hooks/event.ts`, и скрипт пишет строку в `events`:

| Хук Claude Code | Что видно в офисе |
|---|---|
| `SubagentStart` (роль запущена) | Сотрудник садится за стол и печатает |
| `PreToolUse` / `PostToolUse` по `mcp__wb__*` | Облачко над головой: «смотрю остатки…», «читаю отзывы…» |
| `PermissionRequest` на инструмент записи | «!» над директором, карточка «ждёт вашего решения» |
| `SubagentStop` | Сотрудник откидывается на стуле, над столом появляется готовый отчёт |
| `Stop` (директор закончил) | Общий итог на большом экране переговорки |

Кроме того, сервер следит за папкой `reports/` и заносит новые отчёты в `reports`.

Перед началом проверим на текущей версии Claude Code точные имена хуков и поля, которые в них приходят.

## 5. 3D-офис

- **Стек (как сделано):** без сборки и без React — обычный three.js из `node_modules` (сервер отдаёт его по `/vendor/three/`), три файла в `office/web/`. Сервер — встроенный `node:http`, без фреймворка. Так у клиента нечего собирать и меньше зависимостей, которые могут не поставиться. Если фронт разрастётся, его можно перевести на Vite + React Three Fiber, не трогая API.
- **Сцена:** low-poly офис в изометрии. Кабинет директора, финотдел, переговорка, стена с экранами KPI. По клику камера подлетает к столу.
- **Персонажи:** для старта — свободные CC0-наборы (Kenney, Quaternius) с анимациями idle / печатает / ходит. Позже можно сделать фирменных в Blender.
- **Клик по сотруднику** открывает панель: что делает сейчас, последние отчёты, задачи, предложения «было → станет».
- **2D-режим** для слабых ноутбуков: тот же функционал на обычных карточках.

## 7. Ограничения, о которых говорим клиенту честно

- Офис и расписания работают, только пока включён ноутбук и запущен Claude Code / `office:web`.
- С телефона офис не открыть. Решение — облачная версия (раздел 8).
- Обновления: новая zip-сборка или `git pull`.

## 8. Путь в облако: Vercel + Supabase + Agent SDK

Локальная версия — первая ступень. Когда клиенту понадобится офис с телефона и работа 24/7, мы поднимаем ему облачную версию **на том же коде**. Чтобы переезд не превратился в переписывание, локальную версию с первого дня строим на четырёх «переходниках»: у каждого есть локальная и облачная реализация с одним и тем же интерфейсом.

| Переходник | Интерфейс (TypeScript) | Локально (сейчас) | В облаке (потом) |
|---|---|---|---|
| **Хранилище** | `OfficeStore`: агенты, события, задачи, одобрения, отчёты, кэш WB | SQLite `data/office.db` | Supabase Postgres (RLS по `workspace_id`) |
| **Ключи** | `SecretStore`: получить и сохранить ключ, статус ключа | `.env` (`npm run set-key`) | Supabase Vault; форма на фронте пишет через серверный маршрут, назад ключ не отдаётся |
| **Живые события** | `EventBus`: опубликовать событие, подписаться | SSE с локального сервера | Supabase Realtime |
| **Запуск агентов** | `AgentRunner`: задача → роль → поток шагов → результат / предложение | Claude Code клиента + хуки (режим «окна»); Agent SDK на ключе клиента (режим «Одобрить в офисе») | Agent SDK в воркере-контейнере (Railway/Fly) на **коммерческом API-ключе** |

Что для этого делаем уже сейчас:
- **Схема БД с запасом:** во всех таблицах есть `workspace_id` (локально всегда `'local'`), id типа UUID, время в ISO UTC, JSON в отдельных колонках. Тогда миграции SQLite переводятся в Postgres почти механически.
- **Фронт не знает, где он работает:** все запросы идут в `/api/...` и подписку на события, без прямых вызовов SQLite. Тот же фронт потом работает на Vercel (Next.js или Vite + функции), меняется только адрес API.
- **Роли едины:** `.claude/agents/*.md` читает и Claude Code, и Agent SDK (локальный режим API и облачный воркер). Проверка «у ролей запрещены инструменты записи» остаётся в тестах.
- **MCP WB:** добавляем HTTP-транспорт рядом с stdio, чтобы облачный воркер мог подключаться к серверу по сети.
- **Перенос данных:** команда `npm run office:export`. Она выгружает SQLite в JSON/SQL для загрузки в Supabase, так что клиент переезжает со всей историей отчётов и одобрений.

Схема облачной версии:
```
 Браузер / телефон → Vercel (тот же фронт + /api) → Supabase (Postgres, Vault, Realtime, Auth)
                                                         ▲
                       Воркер (контейнер): Agent SDK + MCP WB + синхронизация WB по cron
```

Важно: в облаке Claude работает только на коммерческом API-ключе (наш или клиента). Подписку Claude клиента для облачного сервиса использовать нельзя. Токены оплачиваются отдельно, поэтому в облаке ставим дневной лимит и выводим расход в интерфейс; рутину отдаём Haiku, директора — Sonnet.

**Как продаём** — раздел 9.

## 9. Как продаём: два варианта клиенту

Показываем клиенту обе версии и честно говорим: большинству хватает ноутбука.

| | **Офис на ноутбуке** | **Офис в облаке** |
|---|---|---|
| Где работает | На ноутбуке клиента, пока он включён | Везде: телефон, любой компьютер, 24/7 |
| Кто пользуется | Один человек за этим ноутбуком | Владелец + менеджеры, у каждого свой вход |
| Расписания (утренняя сводка, отзывы каждые 2 часа) | Только когда ноутбук включён | Всегда |
| Claude | Подписка Claude клиента (уже есть или ~$20/мес) | API-ключ, оплата по факту за токены |
| Ежемесячные расходы сверх Claude | **0** | Хостинг: Vercel Pro (~$20), Supabase Pro (~$25), воркер (~$5–10) + токены Claude API |
| Ключи WB и MPSTATS | Только на ноутбуке | В зашифрованном хранилище Supabase |
| Цена нашей настройки | Базовая | Выше: деплой, домен, вход, лимиты, поддержка |
| Кому подходит | Отчёты раз в неделю-месяц, один человек ведёт магазин | Команда, нужен доступ с телефона, ежедневная автоматизация |

> Цены сервисов указаны ориентировочно. Перед каждым коммерческим предложением сверяем их с текущими тарифами Vercel, Supabase, Railway и Anthropic.

**Что говорим клиенту (коротко):**
1. «Вот офис на вашем ноутбуке: все сотрудники, отчёты, одобрения. Ключи никуда не уходят, ежемесячно платить ни за что не нужно.»
2. «Если захотите открывать его с телефона, дать доступ менеджерам и получать сводки, даже когда ноутбук выключен, перенесём в облако со всей историей. Но тогда каждый месяц будут расходы на хостинг и Claude API.»
3. «Если отчёт по WB нужен раз в неделю или раз в месяц, облако вам не нужно, ноутбука хватит. Перейти можно в любой момент.»

**Для README и презентации:** скриншоты офиса, таблица «что умеет каждый сотрудник» (раздел 4) и эта таблица сравнения.
